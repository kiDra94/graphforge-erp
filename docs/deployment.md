# Deploying a public demo

A free setup that gives the README a link to a running Swagger UI.
The backend runs on [Render](https://render.com) as a Docker web service, the database on [Neo4j Aura Free](https://neo4j.com/cloud/platform/aura-graph-database/).
Both have free tiers that need no credit card.

> Render's free tier puts the service to sleep after a period without traffic.
> The first request after that takes around a minute, so say so next to the demo link.

**The live demo runs at [graphforge-erp.onrender.com/api/docs](https://graphforge-erp.onrender.com/api/docs).**
The steps below are what set it up, and what re-creates it if the Aura instance is ever deleted or the demo needs a clean slate.

---

## 1. Database: Neo4j Aura Free

1. Create a free instance in the [Aura console](https://console.neo4j.io).
2. Download the credentials file when it is offered — the password is shown only once.
3. Note the connection URI (`neo4j+s://<id>.databases.neo4j.io`) and the username from that file.

Load schema and demo data from the repository root, with the `cypher-shell` from the Neo4j image:

```bash
docker run --rm -i neo4j:5-community cypher-shell \
  -a 'neo4j+s://<id>.databases.neo4j.io' -u '<username>' -p '<password>' < seed.cypher
```

The last section of the seed prints one row per label.
If the counts match the ones in [data-model.md](data-model.md), the database is ready.

---

## 2. Backend: Render

The repository contains a [`render.yaml`](../render.yaml) Blueprint.

1. Push the repository to GitHub.
2. In the Render dashboard choose **New → Blueprint** and select the repository.
3. Render asks for the three values marked `sync: false`: `NEO4J_URI`, `NEO4J_USERNAME` and `NEO4J_PASSWORD` from step 1.
4. `JWT_SECRET_KEY` is generated by Render, and `DEMO_MODE` is already set to `true` in the Blueprint; nothing to do there.

The first build takes a few minutes.
Afterwards the Swagger UI is at `https://<service-name>.onrender.com/api/docs` — `graphforge-erp` for the live demo, since that is the `name` set in [`render.yaml`](../render.yaml).

Render deploys a push only after its GitHub checks have passed (`autoDeployTrigger: checksPass` in the Blueprint), so a commit that breaks CI never reaches the demo.

---

## 3. Nightly reset: GitHub secrets

[`reset-demo.yml`](../.github/workflows/reset-demo.yml) empties the Aura database every night and loads `seed.cypher` again, so whatever visitors created, changed or deleted is gone the next morning.
It needs the same credentials as the Render service, as repository secrets under **Settings → Secrets and variables → Actions**:

| Secret | Value |
| --- | --- |
| `DEMO_NEO4J_URI` | `neo4j+s://<id>.databases.neo4j.io` |
| `DEMO_NEO4J_USERNAME` | the username from the credentials file |
| `DEMO_NEO4J_PASSWORD` | the password from the credentials file |

To check the setup, or to reset the demo by hand, start the workflow under **Actions → Reset demo data → Run workflow**.

---

## 4. Link it from the README

Add the link near the top of the [README](../README.md), for example:

```markdown
**Live demo:** [Swagger UI](https://<service-name>.onrender.com/api/docs) — click **Authorize** and sign in with `max.mustermann@acme.example` / `demo1234` (the first request may take a minute while the free instance wakes up).
```

## Things to know before going public

- **Everyone shares the demo accounts.** They are listed on the Swagger page, and visitors can create, change and delete data with them. Two things keep that from breaking the demo for the next person:
  - **`DEMO_MODE`** makes the backend refuse the account changes that would lock others out: changing one's own password (`PATCH /api/auth/me/password`) and editing or deleting users (`PATCH`/`DELETE /api/users/{id}`). Everything else stays writable, and the Swagger page says so.
  - **The nightly reset** (step 3) removes everything else visitors left behind. The seed alone would not: it restores the demo data, because every write in it is a `MERGE` on a business key, but leaves what visitors added. That is why the workflow empties the database first.
- **One worker only.** The WebSocket connections live in the memory of one process, which is why the image starts a single uvicorn worker. Render's free tier runs one instance, which fits.
